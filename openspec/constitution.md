# Конституция проекта

Этот документ — единственный источник постоянных инженерных и архитектурных принципов проекта. Все changes, проектные решения и реализация должны соблюдать его. Изменение конституции выполняется явно и не должно происходить незаметно вместе с продуктовой функциональностью.

## 1. Технологические ограничения

- Клиентское приложение использует Nuxt 4, Vue 3 с `<script setup>` и TypeScript.
- Приложение работает в SPA-режиме: `ssr: false`.
- UI-кит — Vuetify 3, управление состоянием — Pinia.
- Пакетный менеджер — npm; разрешённые зависимости фиксируются в `package-lock.json`.
- Замена этих технологий допускается только через отдельное обоснованное изменение.

## 2. Архитектура: pragmatic feature-first

Исходный код Nuxt находится в `app/` и организуется по следующей модели:

```text
app/
├── pages/          # маршруты и композиция экранов
├── layouts/        # общие layout
├── modules/        # продуктовые возможности и их локальная логика
├── domain/         # типы предметной области и контракты репозиториев
├── data/           # реализации доступа к данным
└── shared/         # переиспользуемые компоненты, composables и утилиты
```

### Правила зависимостей

- `pages/` не содержит бизнес-логику и только компонует экраны.
- UI не обращается к данным напрямую и не импортирует реализации из `data/`; доступ выполняется через `GardenRepository`.
- `data/` зависит от контрактов `domain/`, но не от страниц, layout или модулей.
- Модули из `modules/` не импортируют друг друга. Общий код выносится в `domain/` или `shared/`.
- Предметные stores располагаются рядом с соответствующим модулем; текущий маршрут не дублируется в Pinia.
- Пустые каталоги и сегменты «на вырост» не создаются.
- Разумные исключения допускаются для внутренней структуры модулей, но не для направления зависимостей.
- Канонический FSD не является обязательным. Переход к нему рассматривается только при появлении реальных проблем с текущими границами.

## 3. Единый стиль и линтинг

- ESLint с Nuxt-интеграцией обязателен для Vue-, TypeScript- и stylistic-правил.
- `npm run lint` должен завершаться ошибкой при любом warning.
- Массовое отключение правил, подавление warnings и игнорирование файлов ради обхода проверки запрещены.
- Точечные исключения допускаются только при объективной необходимости и не должны становиться способом обхода стандартов.
- Не добавляются конкурирующие источники форматирования. Локальное автоисправление отделено от проверяющей команды.

## 4. Unit-тестирование

- Unit-тесты используют Vitest и Nuxt-совместимое тестовое окружение.
- Новая или изменённая бизнес-логика должна сопровождаться unit-тестами.
- Поведение переиспользуемых компонентов проверяется тестами там, где оно может сломаться без изменения публичного интерфейса.
- Тесты должны проверять наблюдаемое поведение, а не существование файлов или внутренние детали реализации.

## 5. Обязательные quality gates

Перед завершением любого change и до его archive должны успешно выполняться:

```bash
npm run lint
npm run typecheck
npm run test
npm run build
```

- Любая ошибка или warning линтера блокирует завершение change.
- Нельзя отмечать задачи выполненными, если относящиеся к ним проверки падают или не запускались.
- Нельзя архивировать change с непройденными quality gates или незавершёнными задачами.
- CI должен запускать те же команды и считать любой их отказ блокирующим.

## 6. Работа через OpenSpec

- Перед планированием, apply и archive необходимо прочитать эту конституцию.
- Изменения должны быть ограниченными по объёму; весь продукт не реализуется одним change.
- `proposal.md` описывает мотивацию и объём, delta-спецификации — наблюдаемое поведение, `design.md` — технические решения, `tasks.md` — проверяемые шаги.
- Реализация начинается только после явного запроса на apply.
- План пересматривается при изменении решений; код не должен расходиться с артефактами change незаметно.
