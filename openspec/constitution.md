# Конституция проекта

Этот документ — единственный источник постоянных инженерных и архитектурных принципов проекта. Все changes, проектные решения и реализация должны соблюдать его. Изменение конституции выполняется явно, оформляется отдельным изменением и коммитом и не должно происходить незаметно вместе с продуктовой функциональностью.

## 1. Технологические ограничения

- Клиентское приложение использует Nuxt 4, Vue 3 с `<script setup>` и TypeScript.
- Приложение работает в SPA-режиме: `ssr: false`.
- UI-кит — Vuetify 3, управление состоянием — Pinia.
- Пакетный менеджер — npm; разрешённые зависимости фиксируются в `package-lock.json`.
- Замена этих технологий допускается только через отдельное обоснованное изменение.

## 2. Архитектура: pragmatic feature-first

Исходный код Nuxt находится в `app/` и организуется по следующей модели:

```text
app/
├── pages/          # маршруты и композиция экранов
├── layouts/        # общие layout
├── modules/        # продуктовые возможности и их локальная логика
├── domain/         # типы предметной области и контракты репозиториев
├── data/           # реализации доступа к данным
└── shared/         # переиспользуемые компоненты, composables и утилиты
```

### Правила зависимостей

- `pages/` не содержит бизнес-логику и только компонует экраны.
- UI не обращается к данным напрямую и не импортирует реализации из `data/`; доступ выполняется через `GardenRepository`.
- `data/` зависит от контрактов `domain/`, но не от страниц, layout или модулей.
- Модули из `modules/` не импортируют друг друга. Общий код выносится в `domain/` или `shared/`.
- Предметные stores располагаются рядом с соответствующим модулем; текущий маршрут не дублируется в Pinia.
- Пустые каталоги и сегменты «на вырост» не создаются.
- Разумные исключения допускаются для внутренней структуры модулей, но не для направления зависимостей.
- Канонический FSD не является обязательным. Переход к нему рассматривается только при появлении реальных проблем с текущими границами.

## 3. Качество кода и форматирование

- Базовый набор правил качества кода — официальный `@nuxt/eslint` с project-aware flat config; поверх него используются строгие Vue- и type-aware TypeScript-правила.
- Stylistic-правила ESLint не используются.
- Prettier является единственным источником форматирования.
- `npm run lint` должен завершаться ошибкой при любом warning.
- `npm run format:check` должен завершаться ошибкой при любом отклонении от форматирования Prettier.
- Массовое отключение правил, подавление warnings и игнорирование файлов ради обхода проверки запрещены.
- Точечные исключения допускаются только при объективной необходимости и не должны становиться способом обхода стандартов.
- Локальные автоисправление и форматирование отделены от проверяющих команд.

## 4. Unit-тестирование

- Unit-тесты используют Vitest и Nuxt-совместимое тестовое окружение.
- Новая или изменённая бизнес-логика должна сопровождаться unit-тестами.
- Поведение переиспользуемых компонентов проверяется тестами там, где оно может сломаться без изменения публичного интерфейса.
- Тесты должны проверять наблюдаемое поведение, а не существование файлов или внутренние детали реализации.

## 5. Обязательные quality gates

Перед завершением любого change и до его archive должны успешно выполняться:

```bash
npm run audit
npm run audit:production
npm run lint
npm run format:check
npm run typecheck
npm run test
npm run build
```

- Любая ошибка или warning линтера, а также любое нарушение форматирования блокируют завершение change.
- Любое известное замечание полного или production npm audit блокирует завершение change независимо от severity.
- Проверяющие команды audit не выполняют автоматические исправления. `npm audit fix --force` запрещён; совместимые обновления и обоснованные overrides применяются отдельно и затем проходят полный набор quality gates.
- Нельзя отмечать задачи выполненными, если относящиеся к ним проверки падают или не запускались.
- Нельзя архивировать change с непройденными quality gates или незавершёнными задачами.
- CI должен запускать те же команды и считать любой их отказ блокирующим.

## 6. Работа через OpenSpec

- Перед планированием, apply и archive необходимо прочитать эту конституцию.
- Изменения должны быть ограниченными по объёму; весь продукт не реализуется одним change.
- `proposal.md` описывает мотивацию и объём, delta-спецификации — наблюдаемое поведение, `design.md` — технические решения, `tasks.md` — проверяемые шаги.
- Реализация начинается только после явного запроса на apply.
- План пересматривается при изменении решений; код не должен расходиться с артефактами change незаметно.
- Готовность change к archive включает оформление локальных коммитов согласно разделу 10.

## 7. Цветовое оформление

- Основная цветовая база приложения и сайта — семейства `teal` и `blue-grey` из [Material Colors Vuetify](https://vuetifyjs.com/en/styles/colors/#material-colors). Базовый акцентный цвет — `teal #009688`, цвет базовой информации — `blue-grey #607D8B`.
- Оформление должно быть спокойным и преимущественно пастельным: для фонов и больших поверхностей предпочтительны светлые `lighten`-оттенки.
- Яркие `accent`-оттенки применяются только точечно. Пёстрость и смешение множества акцентов недопустимы; другие декоративные палитры добавляются только через явное обновление документации.
- Цвета задаются централизованно через тему и утилиты Vuetify, без произвольных локальных HEX-значений.
- Рамки и скругления единообразны для карточек, кнопок и поверхностей: тонкая граница цвета `teal-lighten-3 #80CBC4` (объявлен в теме как `--v-theme-teal-lighten-3`) и скругление `4px` (стандартный `border-radius-root` Vuetify). Утилиты и пропсы скругления (`rounded-*`, `rounded`, `pill`) не применяются; исключение — icon-кнопки, для которых круглая форма является стандартной.
- Основной цвет текста — `blue-grey-darken-4 #263238`. Для удобства чтения допускается более тёмный нейтральный цвет текста; светлые оттенки `blue-grey` не используются для основного текста на светлом фоне.

## 8. Локализация

- Все видимые пользователю строки должны получаться из i18n-словаря по ключам; хардкод переводимых строк в компонентах запрещён.
- Текущая локаль продукта — русская `ru`. Английский является первым запланированным дополнительным языком, но его словарь, переключатель и локализованные маршруты добавляются отдельным change.
- Layout и компоненты не должны зависеть от длины текста на конкретном языке; используются гибкие размеры и предсказуемый перенос строк с учётом будущих переводов.

## 9. Доступ к данным и API

- До появления backend реализации репозиториев возвращают заранее подготовленные мок-данные, соответствующие контрактам предметной области. UI не зависит от источника данных и не знает, являются ли ответы локальными или серверными.
- Мок-данные для работы приложения относятся к реализациям `data/` и не смешиваются с тестовыми фикстурами. Переход на backend должен выполняться заменой реализаций репозиториев без изменения UI и предметных контрактов.
- Сущности и события предметной области не содержат транспортных сущностей доставки (subscription id, topic, адреса каналов и т.п.); механизм доставки уведомлений проектируется отдельно от доменной модели.
- Моменты времени в API передаются JSON-строками RFC 3339 в UTC с точностью до секунд в каноническом формате `YYYY-MM-DDTHH:mm:ssZ`. Смещения часового пояса и дробные секунды в wire-формате не используются; при сериализации время усекается до секунд, а не округляется. Внутреннее хранение может иметь более высокую точность.
- Календарные даты предметной области передаются в формате `YYYY-MM-DD` без времени и часового пояса и не преобразуются в UTC-моменты. Для серверных вычислений локального дня часовой пояс пользователя передаётся отдельно в формате IANA.
- Идентификаторы сущностей по умолчанию являются непрозрачными строками: приложение использует их только для идентификации и связывания данных и не должно извлекать из них смысл или зависеть от их написания. Публичные идентификаторы backend-ресурсов по умолчанию представляются UUID в JSON-строках; числовые идентификаторы базы данных являются внутренней деталью реализации и не должны без необходимости попадать в API. Mock-реализации могут использовать стабильные человекочитаемые строковые идентификаторы.
- Формат идентификатора должен соответствовать назначению и использованию контракта, а не подгоняться под строковый тип. Если при проектировании предметного контракта и UI явно видно, что числовые идентификаторы удобнее, для них сразу выбирается `number` в TypeScript и числовой JSON-формат. Такое решение обосновывается и фиксируется в спецификации API; неявное смешение строкового и числового представления одного идентификатора не допускается.
- Клиентские и серверные API проектируются на основе [Google API Improvement Proposals](https://google.aip.dev/general). Применимые AIP являются обязательной исходной точкой при проектировании ресурсов, операций, полей, ошибок, совместимости и других API-возможностей. Для нестандартных операций сначала рассматриваются предусмотренные AIP решения, включая custom methods. Отход от применимых AIP крайне нежелателен и допускается только при наличии существенных причин; такое решение должно быть явно обосновано и задокументировано.

## 10. Trunk-based development и ревью

- Разработка ведётся по trunk-based development небольшими проверяемыми инкрементами, попадающими в `master`.
- Обычный коммит должен затрагивать не более 40 файлов; целевой диапазон — 30–40 файлов или меньше. Количество файлов проверяется до коммита, а при превышении лимита работа декомпозируется на более мелкие коммиты.
- Размер коммита контролируется скриптом и pre-commit hook. Будущий CI должен повторно использовать ту же проверку и блокировать изменения, нарушающие лимит.
- Коммит инициализации может превышать 40 файлов только из-за первоначальной установки и настройки инструментов с генерацией конфигурации. Для него используется явный одноразовый override `GARDENLY_ALLOW_LARGE_INIT_COMMIT=1`; даже в этом случае шаги следует разделять, когда это практически возможно.
- Сообщение коммита содержит одно или два коротких предложения и формулируется как название совершённого изменения — отглагольным существительным («Добавление …», «Архивирование …», «Форматирование …»), а не инфинитивом. Ранее созданные коммиты не переименовываются. Указание авторства агента или AI, соответствующие подписи и trailers не добавляются.
- После выполнения всех задач и успешного прохождения quality gates изменения текущего change должны быть оформлены в один или несколько локальных коммитов. До этого change не считается готовым к archive.
- В коммиты включаются только относящиеся к текущему change файлы; параллельно разрабатываемые changes оформляются отдельными коммитами. Отправка в `origin` выполняется только по явному запросу пользователя.
- Архивирование change оформляется отдельным коммитом и не смешивается с реализацией. Пользователь может выполнить архивирование самостоятельно; коммит архивирования выполняется по отдельному явному запросу пользователя.
