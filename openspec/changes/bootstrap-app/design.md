# Design

## Context

Репозиторий не содержит приложения или существующих соглашений по структуре кода. Ограничения и состав основных разделов заданы в [ТЗ](../../../docs/personal-agronom-mvp.md); мотивация описана в [proposal.md](proposal.md), а проверяемое поведение — в [спецификации application-shell](specs/application-shell/spec.md).

## Goals / Non-Goals

**Goals:**

- Задать минимальную структуру Nuxt 4, пригодную для дальнейшего добавления экранов MVP.
- Обеспечить SPA-рендеринг, клиентскую маршрутизацию и единый mobile-first layout.
- Подключить UI-кит и state manager без преждевременного создания предметной модели.
- Установить единый стиль кода и автоматические проверки качества с первого change.

**Non-Goals:**

- Не проектировать репозитории, stores предметной области или схемы данных.
- Не добавлять Capacitor, серверные endpoints, backend и интеграции с внешними API.
- Не наполнять страницы-заглушки функциональностью соответствующих экранов MVP.
- Не настраивать CI-пайплайн в этом изменении.

## Decisions

### Nuxt 4 с pragmatic feature-first архитектурой

Использовать стандартный каталог Nuxt 4 `app/` и файловую маршрутизацию. Внутри него код организуется по назначению и предметным возможностям:

```text
app/
├── pages/
├── layouts/
├── modules/
├── domain/
├── data/
└── shared/
```

- `pages/` содержит только route-компоненты и композицию экранов.
- `modules/` содержит код продуктовых возможностей: `today`, `garden`, `plant`, `task`, `settings`.
- `domain/` содержит типы предметной области и контракт `GardenRepository`.
- `data/` содержит реализации репозитория; UI не импортирует этот каталог.
- `shared/` содержит переиспользуемые компоненты, composables и утилиты.
- Модули не импортируют друг друга; общее выносится в `domain/` или `shared/`.
- Пустые каталоги и сегменты «на вырост» не создаются.

Стандартная структура Nuxt по типам файлов отклонена из-за риска переплетения кода по мере роста. Канонический FSD отклонён для MVP из-за дополнительной церемонии; feature-first сохраняет его основные преимущества и допускает постепенное выделение FSD-слоёв позже без изменения бизнес-логики.

### SPA-режим без серверного рендеринга

Установить `ssr: false` в `nuxt.config.ts`. Это соответствует ТЗ, упрощает будущую упаковку в нативную оболочку и исключает необходимость поддерживать серверный runtime. Альтернатива с SSR или гибридным рендерингом преждевременна для локального офлайн-прототипа.

### Vuetify через Nuxt-интеграцию

Подключить Vuetify 3 через `vuetify-nuxt-module`, использовать его layout- и navigation-компоненты вместо самостоятельного воспроизведения Material Design. Альтернатива ручной регистрации плагина и отдельной настройки сборки стилей даёт больше кода без необходимой сейчас гибкости.

### Единый layout и переиспользуемый компонент навигации

Разместить общий каркас в `app/layouts/default.vue`, а нижнюю навигацию — в `app/shared/components/AppBottomNavigation.vue`. Компонент использует маршруты `/`, `/garden` и `/settings`; активное состояние определяется текущим маршрутом. Это исключает дублирование навигации на страницах и расхождение активного состояния с URL.

### Pinia без предметных stores

Подключить `@pinia/nuxt`, но не создавать store для навигации: текущий раздел уже представлен маршрутом. Предметные stores появятся внутри соответствующих модулей вместе с их изменениями. Альтернатива немедленного создания общего store добавила бы неиспользуемое состояние и дублирование данных маршрутизатора.

### Строгий ESLint как единый источник стиля

Использовать ESLint с Nuxt-интеграцией и строгими Vue-, TypeScript- и stylistic-правилами. Команда `npm run lint` должна завершаться ошибкой при любом warning. Prettier отдельно не добавлять, чтобы избежать двух конкурирующих источников форматирования. Массовое отключение правил и warnings не допускается.

### Vitest для unit-тестов

Использовать Vitest с Nuxt-совместимым test environment и Vue Test Utils для компонентных unit-тестов. В этом change добавить тест навигации, проверяющий пункты, целевые маршруты и активное состояние. Новая бизнес-логика в последующих changes должна сопровождаться unit-тестами; сквозные сценарии не заменяются компонентными тестами.

### Обязательный quality gate

Предоставить команды `npm run lint`, `npm run typecheck`, `npm run test` и `npm run build`. Все четыре команды должны успешно выполняться перед завершением любого change и до archive. Будущий CI должен вызывать те же команды, а не поддерживать отдельный набор проверок.

### npm как исходный пакетный менеджер

Использовать npm и зафиксировать зависимости в `package-lock.json`, поскольку в проекте пока нет выбранного пакетного менеджера. Альтернативные менеджеры не дают преимуществ, необходимых для этого изменения.

## Risks / Trade-offs

- [Несовместимость версий Nuxt и модулей интеграции] → Использовать совместимые актуальные версии, зафиксировать разрешённые версии lockfile и проверить production-сборку.
- [Неявные нарушения границ feature-first модулей] → Поддерживать запрет перекрёстных импортов модулей и доступа UI к `data/`; при росте проекта добавить автоматическую проверку границ отдельным изменением.
- [Строгий линтинг может замедлять внесение изменений] → Использовать локальную команду автоисправления, но в quality gate запускать проверку без автоисправлений и без допуска warnings.
- [Тестирование Vuetify-компонентов требует дополнительного окружения] → Использовать Nuxt-совместимое окружение и Vue Test Utils вместо упрощённых тестов, не проверяющих реальное поведение компонента.
- [Страницы-заглушки могут быть приняты за готовые экраны MVP] → Отображать только заголовки и не добавлять незапланированные элементы продуктовых сценариев.
- [SPA не предоставляет серверного рендеринга] → Принять это ограничение согласно ТЗ; пересматривать режим только отдельным изменением при появлении соответствующего требования.
