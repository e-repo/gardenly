# Design

## Context

`GardenRepository` и `MockGardenRepository` обслуживали прототип модели «один сад», но текущие экраны являются заглушками и не обращаются к репозиторию, поэтому устаревший контракт удаляется в этом же change без сохранения обратной совместимости. Требования находятся в [specs/garden-data-access/spec.md](specs/garden-data-access/spec.md); мотивация — в [proposal.md](proposal.md).

## Goals / Non-Goals

**Goals:**

- Ввести участки и историю ухода без изменения UI и направления зависимостей.
- Удалить legacy-методы, типы и mock-данные прежней модели «один сад / сегодня», не оставляя неиспользуемого кода.
- Сохранить независимые snapshots и воспроизводимые mock-данные.

**Non-Goals:**

- Не добавлять мутации, права доступа и реальную аутентификацию.
- Не моделировать месячный план, погодный rules engine и интервалы обработок.
- Не выбирать структуру координат и параметры погодного провайдера.
- Не проектировать новую модель плановых задач: она появится отдельным change вместе с экраном задач.

## Decisions

### Модель участка и посадки

Добавить:

```ts
interface Plot {
  id: string;
  name: string;
  locationLabel: string;
}
```

`locationLabel` достаточен для отображения локации в первом mock-этапе. Вместо преждевременного добавления координат и provider-specific полей их структура будет определена изменением погодной интеграции.

`Plant` получает обязательный `plotId: string`. `Culture` не меняется и не получает `plotId`: каталог остаётся общим. Две посадки одной культуры на разных участках являются разными записями с разными `id`.

### История фактического ухода

Выделить общий `CareWorkType` из существующего union `Task.type`, добавить `transplanting` и использовать тип в `Task` и `CareEvent`.

```ts
interface CareEvent {
  id: string;
  plotId: string;
  plantId?: string;
  taskId?: string;
  type: CareWorkType;
  performedAt: string;
  productName?: string;
  dosage?: string;
  note?: string;
  photoUrl?: string;
  createdAt: string;
}
```

`performedAt` описывает фактическое выполнение и отличается от `createdAt` — времени создания учётной записи. Оба момента сериализуются по правилам конституции.

`productName` и `dosage` относятся к обработке и поэтому необязательны в общей модели события. Mock-событие обработки обязано заполнить их; валидация обязательности при создании событий относится к будущей команде мутаций. `taskId` необязателен для ручной истории, `plantId` — для работы всего участка или группы растений.

Альтернатива хранить только `Task.completedAt` отклонена: она не сохраняет фактический препарат, дозировку и ручные события, необходимые для проверки интервалов.

### Контракт репозитория

Итоговый read-only контракт:

```ts
getPlots(): Promise<Plot[]>;
getPlant(id: string): Promise<Plant | null>;
getPlantsByPlot(plotId: string): Promise<Plant[]>;
getCultures(): Promise<Culture[]>;
getCurrentWeather(plotId: string): Promise<WeatherForecast | null>;
getCareEvents(plotId: string): Promise<CareEvent[]>;
```

`getPlant()` и `getCultures()` сохраняются из прежнего контракта: они нейтральны к модели «один сад», а каталог культур остаётся общим справочником. Остальные методы прототипа удаляются вместе с типами `Task` и `Settings` и их mock-данными: `getPlants()` заменён участочным `getPlantsByPlot()`, `getTodayWeather()` — `getCurrentWeather()`, дневные задачи и настройки не имеют потребителей и будут перепроектированы отдельными changes.

`CareEvent.taskId` остаётся необязательной непрозрачной строкой: модель плановых задач ещё не существует, а связь понадобится для будущей проверки интервалов обработок.

`getCurrentWeather()` возвращает `null` для неизвестного участка. `getPlantsByPlot()` и `getCareEvents()` возвращают пустой список, что согласуется с существующими коллекционными запросами.

### Mock-набор

Добавить `plots.json`:

- `dacha` — «Дача», «Новая Усмань»;
- `home` — «Дом», «Воронеж, Железнодорожный район».

Все четыре существующие посадки получают `plotId: 'dacha'`. Дом остаётся без посадок, чтобы mock-набор проверял допустимое пустое состояние участка.

Добавить отдельные текущие погодные данные для каждого участка.

Добавить `care-events.json` с событиями дачи разных дат, включая:

- обработку с препаратом, дозировкой и фактическим `performedAt`;
- ручное событие без `taskId`;
- другое событие ухода для проверки сортировки от новых к старым.

Все новые методы возвращают независимые snapshots, как и существующая реализация.

### Тестирование и совместимость

Новые unit-тесты проверяют:

- состав участков и обязательный `plotId` посадок;
- фильтрацию посадок и пустой домашний участок;
- погоду каждого участка и `null` для неизвестного;
- состав и порядок истории, данные обработки и ручное событие;
- независимость snapshots всех новых методов.

Тесты удалённых методов, задач и настроек удаляются; оставшиеся существующие тесты обновляются только с учётом добавленного `plotId`. Текущие экраны `/` и `/garden` не меняются и проходят smoke-проверку.

## Risks / Trade-offs

- [`CareEvent.taskId` ссылается на ещё не существующую модель задач] → Поле остаётся необязательной непрозрачной строкой; контракт плановых задач будет введён отдельным change и не имеет обязательств перед прежним типом `Task`.
- [Домашний участок пуст и не демонстрирует одну культуру на двух участках] → Это намеренный сценарий пустого состава; общая `Culture` проверяется на уровне типов и отдельных тестовых данных при необходимости.
- [Необязательные поля `CareEvent` не обеспечивают полноту обработки на уровне TypeScript] → Mock соблюдает спецификацию, а обязательность при пользовательском вводе проверяет будущая мутация.
- [`locationLabel` недостаточен для реального прогноза] → Погодная интеграция отдельно вводит машинную локацию, не заставляя первый экран зависеть от провайдера.

## Migration Plan

1. Добавить типы и mock-участки.
2. Присвоить всем существующим посадкам участок дачи.
3. Добавить новые методы участочного API.
4. Удалить legacy-методы, типы `Task` и `Settings`, их mock-файлы и тесты.
5. Добавить историю и тесты, затем выполнить полные quality gates и smoke текущих экранов.
6. Последующие UI changes используют только участочный API и проектируют экраны задач и настроек заново.

Откат удаляет новые сущности и методы и восстанавливает прежние mock-файлы; сохранённых пользовательских данных на этом этапе нет.
