# Design

## Context

Приложение работает в SPA-режиме на Nuxt 4, Vue 3, Pinia и Vuetify. `app/layouts/default.vue` уже является общим владельцем `v-app` и нижней навигации высотой 56 px. Store участков и деталей перехватывают ошибки операций, но хранят отдельные `hasCreateError`, а формы рисуют локальные `v-alert`. Мотивация — в [proposal.md](proposal.md), наблюдаемое поведение и границы категорий ошибок — в `specs/`.

## Goals / Non-Goals

**Goals:**

- Иметь один источник состояния текущего ошибочного уведомления и один UI-компонент для всех продуктовых модулей.
- Передавать в общий механизм только локализуемые ключи сообщений, сохраняя исходные ошибки доступными для диагностики в `console.error`.
- Убрать дублирование ошибок создания из feature stores и форм без изменения их boolean-результата и индикаторов pending.
- Гарантировать предсказуемое закрытие, замену и снятие устаревшей ошибки после успешного повторения.

**Non-Goals:**

- Не добавлять очередь уведомлений, success-toast, автоматическое скрытие по таймеру, повтор запроса или сервис удалённого логирования.
- Не перехватывать глобальные исключения рендеринга Vue и не создавать transport-error interceptor до появления реального HTTP-клиента.
- Не менять контракты репозитория, модель ошибок backend и контекстные состояния загрузки или `not found`.
- Не реализовывать редактирование и удаление в этом change; для них фиксируется только переиспользуемый путь уведомлений.

## Decisions

### Общее состояние уведомления

В `app/shared/error-notifications-store.ts` добавляется setup-store `useErrorNotificationsStore` с одним текущим значением:

```ts
interface ErrorNotification {
  id: number;
  messageKey: string;
}

showError(messageKey: string): void;
clearError(messageKey: string): void;
close(): void;
```

`currentNotification` — `shallowRef<ErrorNotification | null>` и возвращается через `readonly`; изменения выполняются только действиями store. `showError()` полностью заменяет текущее значение и увеличивает `id`, поэтому повторная ошибка с тем же текстом остаётся отдельным событием. `clearError(messageKey)` закрывает уведомление только при совпадении ключа, чтобы успешное создание участка не скрыло ошибку другой операции. `close()` безусловно скрывает текущее сообщение по действию пользователя.

Выбран один слот вместо очереди: одновременные toast на мобильном экране перекрывали бы содержимое и усиливали шум. Module-level singleton и event bus не используются: Pinia уже установлена, даёт явное владение состоянием и совместима с принятой архитектурой Nuxt.

### Компонент и размещение

`app/shared/components/AppErrorNotification.vue` подключается один раз в `default.vue` внутри `v-app`. Компонент читает store и использует `v-snackbar` с `v-alert type="error" variant="tonal"`; видимость вычисляется из наличия `currentNotification`, без второго локального источника состояния. `id` используется как `key` для корректного повторного появления и announcement новой ошибки.

Snackbar не имеет таймера и содержит icon-кнопку `mdi-close` с локализованным accessible name и touch-областью не меньше 44 px. Текст выводится через интерполяцию `$t(currentNotification.messageKey)`, без `v-html`. Нижний отступ учитывает навигацию 56 px, визуальный интервал и safe-area; ширина и перенос текста ограничиваются так, чтобы на 390 px не было горизонтальной прокрутки. Цвета, скругление и иконки берутся из существующей темы Vuetify.

### Сообщения и интеграция операций

В `ru.json` добавляется общий раздел `notifications` с `close` и `errors.createPlot` / `errors.createPlant`. Сообщения формулируются без предположения, что причиной всегда являются введённые данные: например, «Не удалось сохранить участок. Попробуйте ещё раз.» Прежние `pages.newPlot.saveError` и `pages.newPlant.saveError` удаляются, чтобы не поддерживать два источника одинаковых строк.

`usePlotsStore.createPlot()` и `usePlotDetailsStore.createPlant()` в `catch` вызывают `showError()` с ключом своей операции, сохраняют `console.error` и возвращают `false`. После полного успешного выполнения они вызывают `clearError()` с тем же ключом. Флаги `hasCreateError` удаляются из состояния и публичного возврата store; `isCreating` и блокировка повторной отправки остаются.

Из `PlotCreateForm.vue` и `PlantCreateForm.vue` удаляются только локальные alert ошибок сохранения. Локальные refs полей не очищаются, поэтому введённые значения переживают ошибку без дополнительной синхронизации. Будущие `update*` и `delete*` используют тот же `showError()` с собственными ключами из общего раздела.

### Сохранение границ ошибок

Общий store не вызывается из `loadGarden()`, `loadPlotDetails()`, `loadPlantsPage()` и чтения данных формы. Соответствующие страницы и секции продолжают владеть своими `hasLoadError`; `isNotFound` также остаётся предметным состоянием чтения. Проверка полей завершается до операции и не создаёт уведомление.

Такое явное разделение выбрано вместо автоматического перехвата всех исключений: одинаковый `Error` от чтения и записи требует разного UX, а вызывающая операция уже обладает этим контекстом.

### Тестирование

- Store уведомлений: показ, закрытие, замена с новым `id`, успешное снятие только совпадающего ключа и сохранение чужого уведомления.
- Компонент с реальными Vuetify, Pinia и `ru.json`: локализованный текст, отсутствие технического текста, доступное закрытие, отсутствие таймера и замена сообщения.
- Feature stores: ключ уведомления при ошибке создания, неизменность предметного состояния, отсутствие `hasCreateError`, снятие своей ошибки после успешного повторения.
- Формы: сохранение значений и маршрута при ошибке, отсутствие встроенного alert, отсутствие уведомления при валидации; существующие тесты загрузки дополняются проверкой, что общее уведомление не создаётся.
- Ручной Chrome-сценарий на 390 px проверяет обе операции создания, закрытие, повторный успех, замену сообщения и доступность нижней навигации.

## Risks / Trade-offs

- [Произвольный строковый ключ может отсутствовать в словаре] → Компонентные и интеграционные тесты используют реальный `ru.json`; новые операции добавляют ключ и проверку сообщения в том же change.
- [Постоянное уведомление может устареть после навигации] → Оно явно закрывается, заменяется новой ошибкой или снимается успешным повторением; автоматический сброс при смене маршрута не скрывает ошибку преждевременно.
- [Одно уведомление скрывает предыдущее при конкурирующих сбоях] → Это осознанный мобильный trade-off; последняя ошибка актуальнее, а исходные ошибки остаются в консоли. Очередь не добавляется без отдельной потребности.
- [Телепортируемый Vuetify overlay сложнее проверять в component-тестах] → Тесты монтируют компонент внутри `v-app` с `attachTo` и проверяют DOM документа, как уже принято для overlays формы посадки.

## Migration Plan

1. Добавить store, общий компонент, i18n-ключи и их изолированные тесты.
2. Подключить компонент в default layout и проверить мобильное позиционирование.
3. Перевести `createPlot` и `createPlant`, удалить локальные флаги и alert, обновить связанные тесты.
4. Проверить неизменность валидации, загрузки основного экрана, `not found` и ошибок секций.
5. Прогнать все quality gates и ручной Chrome-сценарий. После завершения change пересмотреть планы `edit-*` и `delete-*`, чтобы они использовали общий механизм.

Откат выполняется ревертом change: общий host и store удаляются, а локальные флаги и сообщения восстанавливаются вместе с прежними тестами. Постоянных данных и транспортной миграции нет.
