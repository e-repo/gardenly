# Design

## Context

В `app/` существуют только страницы-заглушки, layout и навигация. Каталоги `domain/` и `data/` ещё не созданы. Контракт должен покрыть чтение данных для `garden-list` и `today-overview`, не реализуя их UI и не добавляя будущие мутации. Требования описаны в [specs/garden-data-access/spec.md](specs/garden-data-access/spec.md).

## Goals / Non-Goals

**Goals:**

- Зафиксировать предметные типы и read-only порт `GardenRepository`.
- Создать воспроизводимый локальный mock-набор для первых экранов.
- Обеспечить внедрение реализации без нарушения направления зависимостей.
- Сделать задачи дня независимыми от календарной даты запуска.

**Non-Goals:**

- Не реализовывать backend, не проектировать полный набор сетевых DTO и общую систему синхронизации; из сетевого контракта фиксируются только форматы дат и времени.
- Не добавлять записи истории, изменение статусов, формы и persist.
- Не создавать предметные Pinia stores до появления модулей, которые их используют.

## Decisions

### Предметная модель и read-only порт

В `app/domain/` разместить типы `Plant`, `Culture`, `Task`, `Settings`, `WeatherForecast` и интерфейс `GardenRepository`. Модели растений и задач следуют продуктовому видению, включая `reason`, `instructions`, `warning`, `dueDate`, `dueWindow` и статусы.

`WeatherForecast` содержит только температуру в градусах Цельсия и ограниченное состояние `sunny | partly-cloudy | cloudy | rain`. Этого достаточно для статичной шапки Today без проектирования погодного API.

Интерфейс содержит только:

```text
getPlants()
getPlant(id)
getTodayTasks()
getTasksByPlant(plantId)
getCultures()
getSettings()
getTodayWeather()
```

Методы возвращают Promise даже для локальных данных, чтобы будущая HTTP-реализация сохранила тот же контракт. Полный набор мутаций из итогового ТЗ сюда не переносится до появления соответствующих changes.

### Даты и время в backend-frontend контракте

Глобальное правило зафиксировано в `openspec/constitution.md`. Моменты времени, включая `completedAt` и будущие `createdAt`/`updatedAt`, передаются JSON-строками RFC 3339 в UTC с точностью до секунд. Канонический формат — `YYYY-MM-DDTHH:mm:ssZ`; дробные секунды, смещения вроде `+03:00` и Unix timestamp в wire-формате не используются. При сериализации дробная часть усекается, а не округляется. Внутренняя точность хранения этим не ограничивается.

`dueDate` остаётся локальной агрономической календарной датой `YYYY-MM-DD`, без времени и часового пояса. Её нельзя преобразовывать в полночь UTC или иной момент времени, поскольку это может сместить календарный день у пользователя. `dueWindow` по-прежнему задаёт допустимое окно в днях вокруг этой даты. Для серверного вычисления локального дня и задач «на сегодня» часовой пояс пользователя передаётся отдельно в формате IANA, например `Europe/Moscow`.

Пример пары значений:

```json
{
  "dueDate": "2026-05-10",
  "completedAt": "2026-05-10T06:30:00Z"
}
```

В Go DTO может использовать `time.Time`: `json.Unmarshal` выполняет разбор, а перед `json.Marshal` значение приводится к `UTC().Truncate(time.Second)`. При прямой строковой сериализации используется `UTC().Format(time.RFC3339)`. В JS/TS входящая строка передаётся в `new Date(value)` или `Date.parse(value)`. Для исходящего значения общий helper отбрасывает миллисекунды из `toISOString()` и оставляет суффикс `Z`; внутреннее представление `Date` при этом не меняется. Стандартные парсеры не заменяют отдельную валидацию канонической формы, если она потребуется.

Эти правила не меняют локальную mock-реализацию: текущий календарный день в ней по-прежнему определяется по локальным компонентам даты без внешней date-библиотеки.

### JSON-данные и относительные даты

Мок-данные размещаются в `app/data/mock/`: растения, культуры, задачи, настройки и погода. Это рабочие данные приложения, не тестовые фикстуры.

В JSON задач вместо фиксированной `dueDate` хранится `dueOffsetDays` относительно текущей локальной даты. Для исходной выполненной задачи используется признак `completedToday`. `MockGardenRepository` преобразует mock DTO в предметный `Task` при чтении:

- `dueDate = локальная текущая дата + dueOffsetDays`;
- `completedAt = текущий момент` только для `completedToday`;
- в `getTodayTasks()` входят задачи с `dueDate = today`, а также выполненные сегодня;
- `getTasksByPlant()` возвращает все задачи растения, включая будущие, для последующего блока «Скоро».

Класс получает функцию `now()` через необязательный параметр конструктора. В production используется текущее время, в тестах — фиксированная локальная дата. Собственное форматирование `YYYY-MM-DD` использует локальные компоненты даты, а не UTC `toISOString()`, чтобы не смещать день в часовых поясах. Внешняя date-библиотека не нужна.

### Независимые snapshots

Каждый вызов репозитория заново отображает исходные JSON-объекты в предметные объекты и использует `structuredClone` для справочных данных. Это предотвращает неявную мутацию mock-хранилища потребителем и сохраняет read-only семантику без заморозки объектов, которая могла бы мешать Pinia/Vue.

### Внедрение через Nuxt composition root

`app/plugins/garden-repository.ts` создаёт `MockGardenRepository` и предоставляет его как `$gardenRepository` через Nuxt plugin. Плагин является composition root и единственной точкой сборки, которой разрешено импортировать реализацию из `data/`.

UI и предметные модули получают интерфейс через `useNuxtApp()` и не импортируют ни mock-реализацию, ни JSON. Альтернатива с shared composable отклонена: composable, импортирующий `data/`, размыл бы запрет на доступ UI к реализации.

### Unit-тесты реального поведения

Тесты используют реальный `MockGardenRepository` и его рабочие мок-данные, но фиксированную функцию `now()`. Проверяются:

- исходный состав и чтение известного/неизвестного растения;
- задачи на две разные локальные даты, выполненные сегодня и исключение будущих;
- содержимое причин/инструкций и фильтрация по растению;
- культуры, регион и погода;
- независимость повторных результатов после мутации первого результата.

Проверка существования файлов и внутренней структуры класса не используется.

## Risks / Trade-offs

- [Относительные mock DTO расходятся с предметной моделью] → Ограничить преобразование реализацией репозитория; наружу выходят только полноценные предметные `Task`.
- [Локальные даты чувствительны к часовому поясу] → Не использовать UTC-срез даты; тестировать разные даты через внедрённые часы.
- [Read-only контракт позже расширится мутациями] → Это намеренный инкремент; методы добавляются отдельными changes вместе с реальным поведением.
- [Nuxt plugin становится точкой доступа к data] → Оставить там только создание реализации, без бизнес-логики и UI.

## Migration Plan

Существующих данных и пользователей нет. Изменение добавляет новый порт и реализацию без миграции; откат выполняется удалением новых файлов и plugin без изменения существующих страниц.
