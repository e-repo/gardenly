# ТЗ: «Персональный агроном» — MVP (Версия 2)

**Статус:** черновик обновлённого продуктового видения

**Дата:** ноябрь 2026

---

## 1. Концепция продукта

Мобильное приложение для садоводов-любителей, которое помогает организовать уход сразу за несколькими участками и отвечает на вопрос:

> **Какие работы нужны моим участкам в этом месяце и когда их лучше выполнить?**

Пользователь может вести дачу, домашний участок и другие места отдельно. Для каждого участка приложение хранит состав растений, локацию, план работ, погодный контекст и историю ухода.

Это не просто календарь или энциклопедия растений. Сервис сочетает:

- месячный план обязательных и пользовательских работ;
- краткосрочные рекомендации с учётом погоды;
- понятные инструкции по уходу и обработкам;
- историю фактических работ, необходимую для безопасного планирования следующих.

**Главная ценность MVP:** пользователь видит план по каждому участку, понимает приоритет работ и получает инструкции с учётом конкретных растений, погоды и уже выполненных обработок.

## 2. Технический стек

| Слой             | Технология                                       |
| ---------------- | ------------------------------------------------ |
| Фреймворк        | Nuxt 4 (Vue 3, `<script setup>`, TypeScript)     |
| Режим рендеринга | SPA (`ssr: false`)                               |
| UI-кит           | Vuetify 3 (Material Design)                      |
| Состояние        | Pinia                                            |
| Нативная обёртка | Capacitor (Android; iOS — позже)                 |
| Данные (этап 1)  | Mock-repository поверх локального JSON           |
| Данные (этап 2)  | Http-repository → Supabase / Go API + PostgreSQL |

UI получает данные только через репозиторий и не зависит от того, используются локальные моки или backend:

```text
UI
  -> GardenRepository
       -> MockGardenRepository
       -> HttpGardenRepository
```

Постоянные инженерные правила, форматы данных и требования к API находятся в `openspec/constitution.md` и не дублируются в этом документе.

## 3. Пользователь и аутентификация

Аутентификация нужна для персональных участков, синхронизации и разделения данных пользователей. После входа backend знает профиль пользователя, а права доступа проверяются на сервере.

Первые изменения проектируются **с состояния после успешной аутентификации**:

- вместо предложения войти отображается приветствие и профиль;
- доступны участки текущего пользователя;
- mock-реализация использует заранее подготовленный персональный набор;
- идентификатор пользователя не подменяет проверку владения ресурсами на backend.

Сами экраны входа, регистрация, восстановление доступа и синхронизация выносятся в отдельные изменения.

## 4. Предметная модель

### 4.1. Основные связи

```text
User 1 ----< Plot
Plot 1 ----< Plant >---- 1 Culture
Plot 1 ----< Task
Plant 1 ----< Task
Plot 1 ----< CareEvent
```

`Task` обязательно относится к участку. Связь с конкретным `Plant` необязательна: задача может касаться одной посадки, группы растений или всего участка.

### 4.2. Plot — участок

Участок — верхнеуровневая единица организации ухода: дача, дом или другое место.

Основные данные:

- `id`;
- `name` — пользовательское название;
- `locationLabel` — понятная пользователю локация;
- настройки уведомлений участка;
- текущая погода и краткосрочный прогноз для этой локации.

Локация используется для погодного контекста. Структуру координат, часового пояса и идентификатора погодного провайдера определяет отдельное изменение интеграции погоды.

### 4.3. Culture — культура из общего каталога

Культура не принадлежит участку и используется глобально: яблоня, груша, вишня, смородина и другие растения.

Каталог содержит название, категорию и распространённые сорта. Одна и та же культура или сорт может присутствовать на любом количестве участков. Визуальные обозначения выбираются на стороне UI иконками MDI; emoji в интерфейсе и данных не используются.

### 4.4. Plant — посадка на участке

`Plant` — учётная запись растения в составе конкретного участка, а не глобальная культура из каталога.

Каждая запись:

- принадлежит ровно одному участку через обязательный `plotId`;
- ссылается на одну `Culture`;
- имеет собственные `id`, сорт, год посадки, место внутри участка, количество, фото и пользовательское название.

Одинаковая яблоня Антоновка дома и на даче — две разные записи `Plant`, связанные с одной `Culture`.

Поскольку у записи есть `quantity`, она может описывать как одно растение, так и группу однотипных растений, например три куста смородины в одном ряду.

### 4.5. Task — плановая задача

Задача описывает работу, которую нужно выполнить на участке:

- системную задачу из месячного плана;
- задачу, созданную самим пользователем;
- работу для одной посадки, группы растений или всего участка;
- работу с погодными требованиями или без них.

Типы работ включают обрезку, подкормку, обработку, полив, осмотр и **пересадку**. Пересадка является агрономической задачей и может иметь собственную инструкцию, сроки и погодные ограничения.

Отметка о выполнении пересадки не должна автоматически менять `plotId` или место растения. Обновление учётной записи требует отдельного подтверждения пользователя.

### 4.6. CareEvent — фактическое событие ухода

История обработок обязательна: без неё нельзя определять допустимость следующей обработки и выдерживать интервалы между ними.

`CareEvent` фиксирует факт работы, а не только изменение статуса задачи:

- участок и, когда применимо, растение или группу растений;
- связь с задачей, если событие возникло из неё;
- тип работы;
- фактические дату и время выполнения;
- препарат, действующее вещество и дозировку для обработки, если применимо;
- заметку и фото.

События появляются при завершении задач и при ручном внесении прошлых работ. Возможность добавить историю за прошедший период важна, иначе сервис не сможет корректно рассчитывать следующие обработки для уже существующего сада.

Минимальный интервал не является одной глобальной константой. Он зависит от конкретного правила ухода, препарата, растения и других условий. Правила используют фактическую историю `CareEvent`, чтобы предупредить о слишком ранней повторной обработке.

### 4.7. Инструкции и правила ухода

Сервис хранит структурированные инструкции по обработке и уходу:

- последовательность действий;
- препараты и дозировки;
- зависимость от культуры, возраста и состояния растения;
- сезонные ограничения;
- погодные требования;
- минимальные интервалы между обработками;
- меры безопасности и предупреждения.

Инструкции и правила не дублируются без необходимости в каждой задаче. Связь задач со справочником определяется отдельным изменением месячного планирования.

## 5. Основные разделы и маршруты

Нижняя навигация содержит три пункта: **Мой сад · Задачи · Помощь**. Настройки открываются через отдельную иконку профиля.

| Экран                 | Маршрут                     | Приоритет |
| --------------------- | --------------------------- | --------- |
| Мой сад               | `/garden`                   | P0        |
| Добавление участка    | `/plots/new`                | P0        |
| Карточка участка      | `/plots/:plotId`            | P0        |
| Задачи                | `/tasks`                    | P0        |
| Карточка задачи       | `/tasks/:taskId`            | P0        |
| Добавление растения   | `/plots/:plotId/plants/new` | P0        |
| История ухода         | `/plots/:plotId/history`    | P0        |
| Помощь                | `/help`                     | P1        |
| Настройки             | `/settings`                 | P1        |
| Распознавание по фото | отдельный сценарий          | будущее   |

Маршрут `/` перенаправляет на `/garden`. Детали участков, растений и задач открываются поверх основных разделов.

## 6. Экраны

### 6.1. Мой сад

**Цель:** показать все участки пользователя и дать понятную точку входа в управление ими.

Содержимое:

1. Приветствие или профиль пользователя и иконка настроек.
2. Большая заметная кнопка **«+ Добавить участок»** — основное действие экрана.
3. Карточки участков:
   - название;
   - локация;
   - текущая погода для участка;
   - уведомления;
   - редактирование;
   - переход к составу и задачам участка.
4. Пустое состояние с понятным сценарием добавления первого участка.

Карточки не смешивают растения разных участков в один общий список.

Рекламные блоки интернет-магазина на макете являются будущей возможностью. В первый рабочий экран их не включаем, чтобы не создавать неработающие элементы и не отвлекать от основного действия.

### 6.2. Добавление участка

Минимальный сценарий создаёт участок с пользовательским названием и локацией. После сохранения участок появляется в «Моём саду», а пользователь может перейти к добавлению растений.

Форма, редактирование, настройки уведомлений и удаление проектируются отдельным изменением.

### 6.3. Карточка участка

**Цель:** показать конкретный участок и его состав.

Содержимое:

- название, локация и погода;
- список посадок с культурой, сортом, количеством, возрастом и местом внутри участка;
- добавление растения вручную;
- ближайшие работы;
- переход к истории ухода;
- редактирование участка.

Из этого экрана пользователь открывает конкретную посадку и связанные с ней задачи и события.

### 6.4. Добавление растения

Растение всегда добавляется внутрь выбранного участка. Минимальные поля:

- культура из общего каталога;
- сорт, если известен;
- год посадки;
- место внутри участка;
- количество;
- пользовательское название;
- фото.

После добавления растение появляется в составе участка и может использоваться месячным планом. Автоматическое распознавание культуры по фото рассматривается отдельно.

### 6.5. Задачи

**Цель:** показать полный месячный план и актуальные приоритеты для выбранного участка.

Содержимое:

1. Переключатель участков.
2. Локация и краткий погодный контекст выбранного участка.
3. **Задачи на месяц**:
   - весь перечень системных и пользовательских работ;
   - не только погодозависимые задачи;
   - пересадка и другие работы, запланированные владельцем;
   - отметка о выполнении;
   - переход к инструкции.
4. **Приоритетные рекомендации**:
   - задачи, для которых наступило подходящее погодное окно;
   - объяснение рекомендации;
   - переход к подробной инструкции.

Месячный план и краткосрочный прогноз не смешиваются. План строится на месяц, а прогноз используется только на доступном и достаточно надёжном горизонте — ориентировочно 7–14 дней, без иллюзии точного прогноза на весь месяц.

Приоритетная рекомендация не должна дублировать отдельную сущность задачи. Это представление плановой задачи, для которой правила определили подходящие условия.

### 6.6. Карточка задачи

Содержит:

- название, участок и растения;
- срок и статус;
- причину рекомендации;
- подробную инструкцию;
- препарат, дозировку и меры безопасности, если применимо;
- погодные ограничения;
- информацию о допустимом интервале с учётом истории;
- действия выполнения и планирования.

Завершение обработки создаёт `CareEvent` с фактическими данными выполнения.

### 6.7. История ухода

История доступна по участку и конкретным растениям. Она показывает хронологию фактических работ, включая обработки, подкормки, обрезку, пересадку и ручные записи.

Для обработок отображаются дата, препарат, дозировка и растения. Пользователь может внести прошлое событие вручную. История используется не только для просмотра, но и правилами планирования следующих работ.

### 6.8. Помощь и настройки

Содержимое раздела «Помощь» определяется отдельным изменением. В настройках находятся профиль, уведомления, единицы измерения, информация о приложении и служебные действия.

Регион не является одной глобальной настройкой сада: локация и погодный контекст принадлежат каждому участку отдельно.

---

## 7. Распознавание растений по фото

Отдельная будущая возможность и потенциальный платный сценарий:

```text
Фото растения
  -> предложение культуры и, при возможности, сорта
  -> проверка и подтверждение пользователем
  -> добавление Plant в выбранный Plot
```

Сервис не должен без подтверждения считать распознавание окончательным: пользователь может не знать точное название, а ошибка в культуре влияет на инструкции и безопасность обработок.

В первые изменения фотораспознавание, диагностика заболеваний и ИИ-консультант не входят.

## 8. Нефункциональные требования

- **Mobile-first:** вёрстка под ширину около 390 px, touch-области не менее 44 px, отсутствие зависимости от hover.
- **Читаемость:** спокойное оформление, понятный основной CTA, отсутствие перегрузки главного экрана.
- **Действия:** не отображаются неработающие кнопки, ссылки и чекбоксы.
- **Анимации:** только `transform` и `opacity`; стандартные переходы Vue и Vuetify.
- **Производительность:** время до интерактивности на среднем Android — менее 3 секунд на целевом устройстве.
- **Офлайн-прототип:** mock-этап работает с локальными данными без сети.
- **Android:** аппаратная кнопка «назад» использует историю роутера; учитываются safe area, splash screen и иконки.
- **Язык:** русский; английский добавляется отдельным изменением.

## 9. Границы первых изменений

Первые изменения не включают:

- реальные регистрацию, аутентификацию и синхронизацию;
- backend и погодного провайдера;
- полный rules engine агрономических рекомендаций;
- фотораспознавание и ИИ-диагностику;
- push-уведомления;
- рекламу и платёжную систему;
- iOS и специальную десктопную вёрстку.

При этом предметные связи участков, посадок, задач и истории закладываются сразу, чтобы последующая замена моков не потребовала переписывания UI.

---

## 10. Критерии готовности MVP

1. Пользователь видит свои участки, может добавить участок и перейти к его составу.
2. Пользователь может добавить растение в участок вручную.
3. По выбранному участку отображаются месячный план и приоритетные рекомендации без дублей.
4. Пользователь может открыть инструкцию и завершить задачу.
5. Завершение обработки сохраняет фактическое событие в истории.
6. Пользователь может внести прошлую обработку и увидеть её в истории.
7. Правила учитывают историю и не предлагают повторную обработку раньше допустимого интервала без понятного предупреждения.
8. Основные сценарии работают без тупиков и неработающих controls на мобильном экране.
9. APK собирается и стабильно работает на целевом Android-устройстве.

## 11. План инкрементов

Каждый инкремент оформляется отдельным OpenSpec change. Названия активных changes могут уточняться при пересмотре без изменения последовательности зависимостей.

| Порядок | Change                    | Содержимое                                                                        |
| ------- | ------------------------- | --------------------------------------------------------------------------------- |
| 1       | `plots-data-foundation`   | Участки, обязательный `Plant.plotId`, история ухода и согласованные моки.         |
| 2       | `garden-plots-overview`   | Экран «Мой сад», карточки участков, рабочее добавление участка и новая навигация. |
| 3       | `plot-details`            | Состав конкретного участка и переходы к растениям и истории.                      |
| 4       | `add-plant`               | Добавление посадки внутрь участка.                                                |
| 5       | `monthly-tasks`           | Месячный план, переключатель участков и пользовательские задачи.                  |
| 6       | `care-history`            | Просмотр и ручное внесение фактических событий ухода.                             |
| 7       | `task-details-completion` | Инструкции и завершение задачи с записью `CareEvent`.                             |
| 8       | `weather-recommendations` | Краткосрочный прогноз и погодные окна без месячного прогноза.                     |
| 9       | `care-interval-rules`     | Проверка интервалов по фактической истории обработок.                             |
| 10      | `help-and-settings`       | Содержимое разделов «Помощь» и «Настройки».                                       |

После базового MVP: реальные auth/backend/синхронизация, погодный провайдер, расширение правил, платное распознавание растений по фото, рекламные интеграции и iOS.
